이 단계는 관리 화면에서 편집할 시대 설정 테이블을 만드는 작업입니다. 캐릭터 저장, AI 생성, 20년 시간 진행, 점수 지급은 아직 연결하지 않습니다. 관리자 편집 화면의 DB 조회·저장은 후속 작업으로 완료했으며 [세계 편집실 안내](ADMIN.md)를 참고하세요.

- 상태: `draft` — 관리자만 보며 편집할 수 있습니다.

테이블 생성과 초기 데이터 입력은 Supabase 연결 도구로 실제 프로젝트에 완료했습니다. SQL 파일을 다시 실행할 필요는 없습니다.

[테이블 생성 SQL](../supabase/migrations/20261103045107_era_catalog.sql)과 [초기 데이터 SQL](../supabase/seed-era.sql)은 변경 이력을 위한 소스입니다. 생성 SQL은 같은 이름의 기존 테이블을 덮어쓰지 않습니다. 초기 데이터 SQL을 다시 실행해도 이미 있는 행은 수정하지 않습니다.

다른 프로젝트에 재현할 때만 생성 SQL → 초기 데이터 SQL 순서로 적용합니다. 이후 변경은 새 마이그레이션으로 기록합니다.

## 편집할 테이블

| 테이블           | 한 행의 의미                     | 주로 수정할 열                                                                                               |
| ---------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `era_templates`  | 시대 유형 한 개                  | `name`, `description`, `duration_years`, `version`, `status`                                                 |
| `era_objectives` | 한 번만 점수를 얻을 수 있는 과제 | `name`, `description`, `points`, `sort_order`                                                                |
| `era_outcomes`   | 성과 점수별 결과 한 구간         | `name`, `min_score`, `max_score`, `world_result`, `fame_reward`, `contribution_reward`, `legacy_reward_code` |

`id`는 한글 표시 이름과 별개인 고정 식별자입니다. 다른 행과 연결되므로 생성 후에는 바꾸지 않는 것을 권장합니다. `era_id`는 부모 시대의 `id`입니다. `created_at`, `updated_at`은 자동 관리합니다.

`condition_code`, `target_key`는 앞으로 게임 엔진과 AI가 참조할 정해진 조건·슬롯입니다. 이 열에 새로운 문자열을 넣는 것으로 새로운 게임 규칙이 실행되지는 않습니다. 현재 DB가 허용하는 코드는 아래와 같습니다.

| 코드                   | 뜻                    |
| ---------------------- | --------------------- |
| `CLUE_FOUND`           | 지정 단서 확보        |
| `INFILTRATORS_EXPOSED` | 잠입 조직의 정체 확인 |
| `DEFENSE_SUCCESS`      | 지정 지역 보호        |
| `ALLIANCE_SECURED`     | 지정 세력 협력 확보   |
| `SUPPLY_BASE_STOPPED`  | 보급 거점 무력화      |
| `RITUAL_STOPPED`       | 핵심 의식 중단        |

보상 코드는 `NONE`, `SECT_LEGACY_CHOICE`, `SPECIAL_LEGACY_CHOICE`만 허용합니다. 실제 전승 선택과 보상 지급은 다음 단계의 엔진 작업입니다. 현재 웹앱에는 아직 명성·시대 공헌 지급 기능이 없습니다.

## 초안과 공개

초기 데이터는 `draft` 상태입니다. Supabase 관리 화면에서는 확인하고 수정할 수 있지만 일반 게임 클라이언트는 읽지 못합니다.

검토 후 다음 SQL을 실행하면 공개됩니다.

```sql
update public.era_templates
set status = 'published'
where id = 'demonic_rise_v1';
```

공개할 때 다음을 DB에서 검사합니다.

- 과제 점수의 합계가 정확히 100인지
- 결과 구간이 겹치거나 비지 않고 0~100을 모두 포함하는지
- 필수 과제 ID가 해당 시대 안에 실제 존재하는지
- 최하위 결과에 필수 과제가 없어 어떤 진행 상태에도 결산 결과를 고를 수 있는지

공개 후에도 유효성을 깨는 변경은 저장되지 않습니다. 여러 행의 점수를 조정하려면 먼저 `status`를 `draft`로 바꾸고 편집한 뒤 다시 `published`로 바꿉니다. 트랜잭션 안에서 여러 행을 한꺼번에 수정하면 마지막 상태로 검증합니다.

이후 게임을 연결할 때는 시작한 시대의 데이터 전체를 복사해 고정하고, DB 수정본은 다음 시대·새 게임에만 적용하도록 구현해야 합니다. **이 SQL만으로 진행 중인 게임의 버전 고정 기능이 생기는 것은 아닙니다.**

## 권한

- Supabase 관리 화면의 관리자: 테이블 편집 가능
- 게임의 `anon` / 일반 로그인 계정: 공개된 시대만 읽을 수 있으며, 관리자 허용 목록의 인증된 이메일만 RLS와 RPC를 통해 편집 가능
- 초안 데이터: 일반 클라이언트에서 읽기 불가, 인증된 관리자만 조회 가능
- 이 세 테이블에는 숨겨진 개인 정보나 비밀 설정을 넣지 않습니다. `published` 행은 공개 조회 대상입니다.

실제 게임 조회를 연결할 때는 프로젝트 URL과 publishable 키만 클라이언트에 사용합니다. service_role/secret 키는 클라이언트에 넣지 않습니다. 연결 키는 다음 단계에서 프로젝트 설정에 구성합니다.

## 완료한 검증

- 로컬 Postgres 호환 엔진에서 스키마·초기 데이터 재실행·점수 합계·초안 숨김·읽기 허용·수정 거부·잘못된 공개 거부를 검사했습니다.
- 실제 Supabase에서 3개 테이블, 과제 10개, 합계 100점, 5개 결과 구간을 조회했습니다.
- 실제 DB의 트랜잭션 안에서 임시 공개 → 공개 유효성 검사 → 비로그인 읽기 성공 → 수정 권한 거부를 검사하고 전체 롤백했습니다. 최종 상태는 `draft`입니다.
- Supabase 보안·성능 Advisor의 지적 사항은 없었습니다.

자동 검사는 `npm run test:db`로 실행합니다. 임시 메모리 Postgres에서 실행하며 실제 Supabase 데이터는 변경하지 않습니다. CI에도 포함했습니다.
